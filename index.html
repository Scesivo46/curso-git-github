    Módulo 1

    Bienvenida: ¿qué es Git y para qué sirven GitHub y GitLab?

    Al terminar este curso sabrás crear repositorios, guardar versiones de tu trabajo, usar ramas, subir tus proyectos a GitHub o GitLab y colaborar con otras personas.

    ⏱ 3–4 horas🧪 Simulador incluido💻 Pensado para Windows📱 Se puede leer en el móvil🎯 Nivel: cero absoluto

    El problema que resuelve Git

    Seguro que alguna vez has tenido una carpeta así:

    trabajo_final.docx
trabajo_final_v2.docx
trabajo_final_v2_corregido.docx
trabajo_final_DEFINITIVO.docx
trabajo_final_DEFINITIVO_ahora_si.docx

    Esto es control de versiones manual: copias y copias de un mismo archivo para no perder nada. Funciona... hasta que no sabes qué cambiaste en cada copia, o dos personas editan a la vez.

    Git es un programa que hace esto por ti de forma ordenada: guarda "fotos" (llamadas commits) de tu proyecto cada vez que tú se lo pides, con un mensaje que explica qué cambiaste, quién y cuándo. Puedes volver a cualquier foto anterior cuando quieras.

    Git, GitHub y GitLab: tres cosas distintas

    🛠 Git

    Un programa que instalas en tu ordenador. Funciona sin internet. Lleva el historial de versiones de tus carpetas. Es el mismo para todo el mundo.

    GitHub

    Una web (github.com, de Microsoft) donde subes tus repositorios de Git. Es la más popular: ahí está casi todo el software libre.

    GitLab

    Otra web (gitlab.com) que hace lo mismo. Muy usada en empresas porque además puede instalarse en servidores propios.

    Analogía rápidaGit es la cámara de fotos. GitHub y GitLab son dos álbumes online distintos donde puedes subir esas fotos para compartirlas y no perderlas. La cámara funciona igual suba las fotos a uno o a otro.

    Cómo leer este curso

    Todo lo que se hace con Git en la terminal es idéntico para las dos plataformas. Solo cambian la web y algunos nombres. Cada vez que un paso sea distinto verás las dos variantes, una junto a otra (o una debajo de otra en el móvil):

    GitHub

    Instrucciones para GitHub.

    GitLab

    Instrucciones para GitLab.

    💡 ¿Solo te interesa una?En el menú (☰ en el móvil) tienes el selector "Mostrar instrucciones de": elige GitHub, GitLab o ambas. El curso se adapta al instante.

    ¿Para qué sirve en la vida real?

    ⏪ Viajar en el tiempo

    ¿Rompiste algo? Vuelve a la versión de ayer en segundos.

    🧪 Experimentar sin miedo

    Prueba ideas en una "rama" aparte sin tocar la versión buena.

    👥 Trabajar en equipo

    Varias personas en el mismo proyecto sin pisarse.

    🌍 Publicar

    Comparte código, documentación o incluso una web gratis (GitHub Pages o GitLab Pages).

    Aunque se asocia a programadores, Git sirve para cualquier proyecto basado en archivos de texto: código, webs, documentación en Markdown, guiones, scripts de automatización, configuraciones…

    ⚠️ Ojo con los archivos grandesGit no está pensado para vídeos, audios o archivos binarios pesados (proyectos de Premiere, .mp4, .psd…). GitHub rechaza archivos de más de 100 MB y GitLab.com limita el tamaño total del repositorio en el plan gratuito. Para eso existe la extensión Git LFS. Usa Git para el código, scripts y documentos de texto de tus proyectos.

    Módulo 2

    Instalación y configuración

    Dejamos tu ordenador listo en 10 minutos. Solo se hace una vez y vale para GitHub y GitLab.

    1. Instalar Git en Windows

    1. Ve a git-scm.com/downloads y descarga la versión para Windows.
    2. Ejecuta el instalador. Puedes dejar todas las opciones por defecto. Solo dos recomendaciones:
      • En "Choosing the default editor", elige Visual Studio Code o Notepad (por defecto viene Vim, que es difícil para empezar).
      • En "Adjusting the name of the initial branch", elige Override… → main.
    3. Al terminar tendrás un programa nuevo: Git Bash, una terminal preparada para Git. También puedes usar PowerShell o la terminal de VS Code.

    Comprueba que está instalado abriendo Git Bash (o PowerShell) y escribiendo:

    $ git --version
git version 2.47.1.windows.1
    💡 ¿Qué es una terminal?Una ventana donde das órdenes al ordenador escribiendo en vez de con clics. En este curso, las líneas que empiezan por $ son órdenes que escribes tú (sin escribir el $). El resto de líneas es lo que responde el ordenador. Usa el botón Copiar de cada bloque.

    Comandos básicos de terminal que vas a necesitar

    pwdMuestra en qué carpeta estáspwd
    lsLista los archivos de la carpetals
    cdEntra en una carpeta (cd .. sube una)cd Documentos

    💡 Truco de WindowsEn el Explorador de archivos, clic derecho dentro de una carpeta → Open Git Bash here (o "Mostrar más opciones"). Así la terminal se abre directamente en esa carpeta.

    2. Decirle a Git quién eres

    Cada commit lleva el nombre y email de quien lo hizo. Configúralo una vez. Usa el mismo email que tengas (o vayas a tener) en tu cuenta de GitHub o GitLab: así la web asociará tus commits a tu perfil.

    $ git config --global user.name "Tu Nombre"
$ git config --global user.email "tu-email@ejemplo.com"
$ git config --global init.defaultBranch main
# Opcional: usar VS Code como editor para los mensajes
$ git config --global core.editor "code --wait"

    Para comprobar lo configurado:

    $ git config --global --list
user.name=Tu Nombre
user.email=tu-email@ejemplo.com
init.defaultbranch=main
    ¿Qué significa --global?Que la configuración vale para todos los repositorios de tu usuario. Si en un proyecto concreto quieres otro email (por ejemplo, el del trabajo en el GitLab de tu empresa), entra en esa carpeta y repite el comando sin --global.

    3. Crear tu cuenta

    GitHub
    1. Entra en github.com/signup.
    2. Elige un nombre de usuario: aparecerá en la URL de tus proyectos, github.com/tu-usuario.
    3. Activa la verificación en dos pasos: foto de perfil → Settings → Password and authentication → Enable two-factor authentication. GitHub la exige.
    GitLab
    1. Entra en gitlab.com/users/sign_up.
    2. Elige un nombre de usuario: aparecerá en la URL de tus proyectos, gitlab.com/tu-usuario.
    3. Activa la verificación en dos pasos: foto de perfil → Edit profile → Account → Enable two-factor authentication.
    4. GitLab puede pedirte verificar tu identidad (teléfono o tarjeta, sin cobro) para usar sus servidores de automatización gratuitos, que necesitarás para publicar una web con GitLab Pages.

    4. (Recomendado) Herramientas cómodas

    Visual Studio Code

    Editor gratuito con Git integrado: ves cambios en colores, haces commits con botones y resuelves conflictos fácilmente. Sirve para las dos plataformas.

    GitHub

    GitHub Desktop: aplicación oficial con interfaz gráfica para Git. Para VS Code existe la extensión GitHub Pull Requests, que permite revisar PR sin salir del editor.

    GitLab

    No hay aplicación de escritorio oficial. Usa VS Code con la extensión oficial GitLab Workflow (merge requests, issues y pipelines dentro del editor) o un cliente genérico de Git.

    Aprende primero los comandos: así entenderás lo que hacen los botones de cualquier herramienta.

    Módulo 3

    Conceptos clave: las tres zonas de Git

    Si entiendes este módulo, entiendes Git. Todo lo demás son variaciones.

    Dentro de tu ordenador, Git maneja tus archivos en tres zonas, más una cuarta cuando usas GitHub o GitLab:

    📁 Directorio de trabajoTus archivos tal cual los ves y editas.
    →git add
    📦 Staging
    (área de preparación)    Lo que has elegido para la próxima foto.
    →git commit
    🗄 Repositorio localHistorial de fotos (commits) guardadas en la carpeta oculta .git.
    ⇄push / pull
    ☁️ RemotoCopia del repositorio en la nube: GitHub o GitLab

    La analogía de la mudanza 📦

    • Directorio de trabajo = tu casa, con todas tus cosas por medio.
    • Staging = la caja abierta donde vas metiendo lo que quieres enviar en este viaje (git add).
    • Commit = cerrar la caja, ponerle una etiqueta ("libros de la cocina") y guardarla en el almacén (git commit).
    • Push = mandar las cajas etiquetadas a un guardamuebles externo (GitHub o GitLab).
    ¿Por qué existe el staging? ¿No sería más fácil guardar todo de golpe?Porque te permite hacer commits ordenados. Imagina que has corregido una falta de ortografía y añadido una sección nueva. Con el staging puedes guardarlos en dos commits separados, cada uno con su mensaje claro.

    ¿Qué es exactamente un commit?

    Un commit es una instantánea de todos los archivos preparados, con:

    • Un identificador único (hash), como a3f9c21. Es la "matrícula" del commit. GitHub y GitLab lo muestran igual.
    • El autor, la fecha y un mensaje.
    • Un enlace al commit anterior (su "padre"). Así se forma una cadena: el historial.

    Los estados de un archivo

    EstadoQué significaCómo lo ves en git status
    U Sin seguimientoArchivo nuevo que Git aún no vigilaUntracked files
    M ModificadoGit lo vigila y ha cambiado desde el último commitChanges not staged for commit
    A PreparadoEstá en el staging, entrará en el próximo commitChanges to be committed
    ✓ ConfirmadoGuardado en un commit y sin cambios nuevosnothing to commit, working tree clean

    Módulo 4 · Práctica

    Tu primer repositorio, paso a paso

    Vamos a crear un pequeño proyecto: un recetario en texto. Todo este módulo ocurre en tu ordenador, así que es igual para GitHub y GitLab. Abre Git Bash y sigue los pasos (o usa el simulador).

    Paso 1 · Crear la carpeta e iniciar Git

    $ cd ~/Documents
$ mkdir recetario
$ cd recetario
$ git init
Initialized empty Git repository in C:/Users/tu/Documents/recetario/.git/

    git init crea una carpeta oculta llamada .git. Ahí vive todo el historial. No la toques ni la borres: si la borras, la carpeta deja de ser un repositorio (tus archivos siguen, pero pierdes el historial).

    Paso 2 · Crear un archivo y mirar el estado

    Crea un archivo README.md. Puedes hacerlo con tu editor o desde la terminal:

    $ echo "# Mi recetario" > README.md
$ git status
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
        README.md

nothing added to commit but untracked files present (use "git add" to track)
    💡 Hábito de orogit status es tu mejor amigo. Úsalo antes y después de cada orden: te dice exactamente en qué situación estás y suele sugerirte el siguiente paso.

    Paso 3 · Preparar (add) y confirmar (commit)

    $ git add README.md
$ git status
On branch main

No commits yet

Changes to be committed:
  (use "git rm --cached <file>..." to unstage)
        new file:   README.md

$ git commit -m "Crea el README del recetario"
[main (root-commit) 4e1b2a7] Crea el README del recetario
 1 file changed, 1 insertion(+)
 create mode 100644 README.md

    ¡Enhorabuena! 🎉 Acabas de guardar la primera versión de tu proyecto.

    Paso 4 · Seguir trabajando

    Añadimos una receta y modificamos el README:

    $ echo "Tortilla: huevos, patatas, aceite, sal" > tortilla.txt
$ echo "Recetas fáciles para el día a día" >> README.md
$ git status
On branch main
Changes not staged for commit:
        modified:   README.md

Untracked files:
        tortilla.txt

# Añadir TODO lo que ha cambiado de una vez:
$ git add .
$ git commit -m "Añade receta de tortilla y descripción"
[main 9c03f11] Añade receta de tortilla y descripción
 2 files changed, 2 insertions(+)
    git add . vs git add archivoEl punto significa "todo lo de esta carpeta". Es cómodo, pero revisa antes con git status para no añadir cosas que no quieres (archivos temporales, contraseñas…).

    Paso 5 · Ver el historial

    $ git log --oneline
9c03f11 (HEAD -> main) Añade receta de tortilla y descripción
4e1b2a7 Crea el README del recetario

    HEAD es un puntero que indica "dónde estás ahora". HEAD -> main significa: estás en la rama main, en su último commit.

    Cómo escribir buenos mensajes de commit

    ✅ Bien

    Añade receta de gazpacho
    Corrige cantidades de la tortilla
    Reorganiza el índice por categorías

    ❌ Mal

    cambios
    asdf
    arreglado ahora sí
    varias cosas

    Regla práctica: el mensaje debe completar la frase "Si aplico este commit, el proyecto…" → "…añade receta de gazpacho". Corto (menos de ~50 caracteres), en presente y describiendo qué cambia.

    El archivo .gitignore

    Hay archivos que nunca deberían entrar en el repositorio: temporales, configuraciones personales, contraseñas, carpetas enormes… Crea un archivo llamado .gitignore en la raíz y escribe uno por línea:

    # Archivos del sistema
Thumbs.db
desktop.ini
.DS_Store

# Secretos y configuraciones locales
.env
claves.txt

# Carpetas generadas o pesadas
node_modules/
render/
*.log
*.mp4

    Git ignorará todo lo que coincida. *.log significa "cualquier archivo que acabe en .log". Recuerda hacer commit del propio .gitignore.

    GitHub

    Al crear un repositorio en la web puedes elegir una plantilla de .gitignore ya hecha (Node, Python, VisualStudio…) en el desplegable "Add .gitignore".

    GitLab

    Desde la web del proyecto: botón + → New file, escribe .gitignore como nombre y GitLab te ofrecerá un selector de plantillas (Apply a template).

    ⚠️ Nunca subas contraseñasSi una clave llega a un commit y la subes a GitHub o GitLab, considérala comprometida aunque la borres después: queda en el historial. Cámbiala de inmediato.

    Módulo 5

    Ver el historial y deshacer cambios

    Aquí está la magia de Git: equivocarse deja de dar miedo.

    Mirar el pasado

    # Historial completo (pulsa q para salir)
$ git log
commit 9c03f11d2b... (HEAD -> main)
Author: Tu Nombre <tu-email@ejemplo.com>
Date:   Wed Nov 18 10:42:13 2026 +0100

    Añade receta de tortilla y descripción

# Historial resumido, una línea por commit
$ git log --oneline
# Con dibujo de ramas
$ git log --oneline --graph --all
# Ver qué cambió exactamente en un commit
$ git show 9c03f11

    Una vez subido, también puedes ver el historial en la web:

    GitHub

    En la página del repositorio, enlace "N commits" (icono de reloj) sobre la lista de archivos. Pulsa un commit para ver sus cambios en rojo y verde.

    GitLab

    Menú lateral Code → Commits. Para ver las ramas dibujadas: Code → Repository graph.

    Ver diferencias antes de guardar

    $ echo "Tortilla: huevos, patatas, cebolla, aceite, sal" > tortilla.txt
$ git diff
diff --git a/tortilla.txt b/tortilla.txt
-Tortilla: huevos, patatas, aceite, sal
+Tortilla: huevos, patatas, cebolla, aceite, sal
# Ver lo que ya está en staging:
$ git diff --staged

    Las líneas con - (rojo) son las que se quitan y las de + (verde) las que se añaden. ¡Debate de la cebolla resuelto en el historial! 🧅

    Recetas para deshacer (de menos a más grave)

    SituaciónSolución
    He cambiado un archivo y quiero descartar los cambios (volver a como estaba en el último commit)git restore archivo
    He hecho git add de algo que no quería (sacarlo del staging), sin perder los cambiosgit restore --staged archivo
    Me he equivocado en el mensaje del último commit (y aún no lo he subido)git commit --amend -m "Mensaje bueno"
    Se me olvidó añadir un archivo al último commitgit add olvidado.txt y git commit --amend --no-edit
    Un commit antiguo introdujo un error y quiero anularlo de forma seguragit revert <hash> (crea un commit nuevo que deshace el otro)
    Quiero guardar cambios a medias un momento sin hacer commitgit stash … y luego git stash pop

    Ejemplo práctico: recuperar un archivo estropeado

    # ¡Ups! Sobrescribimos la receta por error
$ echo "lo que sea" > tortilla.txt
$ git status
        modified:   tortilla.txt
# Volver a la versión del último commit
$ git restore tortilla.txt
$ cat tortilla.txt
Tortilla: huevos, patatas, aceite, sal

    Ejemplo práctico: anular un commit ya subido

    $ git log --oneline
b71e0c2 (HEAD -> main) Borra la sección de postres
9c03f11 Añade receta de tortilla y descripción
$ git revert b71e0c2 --no-edit
[main e5d4f90] Revert "Borra la sección de postres"
    GitHub

    Si el cambio entró mediante un pull request, en la página del PR ya fusionado tienes el botón Revert: crea automáticamente un PR nuevo que lo deshace.

    GitLab

    En un merge request ya fusionado, o en la página de cualquier commit, tienes el botón Revert: GitLab crea el commit de anulación (y puede abrir un merge request con él).

    ⚠️ Cuidado con git reset --hardVerás este comando en internet. Borra cambios sin preguntar y reescribe el historial. Como principiante, prefiere restore y revert: son seguros. Y nunca uses --amend o reset sobre commits que ya has subido al remoto y comparte más gente.
    Ramas protegidasTanto GitHub como GitLab permiten proteger main para que nadie pueda reescribir su historial. En GitLab viene activado por defecto; en GitHub se configura en Settings → Branches / Rules.

    Viajar a una versión antigua (solo mirar)

    $ git switch --detach 4e1b2a7
# ...miras los archivos tal y como estaban...
$ git switch main

    Mientras estás en un commit antiguo, Git dice que estás en "detached HEAD" (cabeza desacoplada). Suena alarmante pero solo significa "no estás en ninguna rama". Vuelve con git switch main.

    Módulo 6

    Ramas (branches) y fusiones (merge)

    Las ramas te permiten trabajar en algo nuevo sin estropear lo que ya funciona.

    ¿Qué es una rama?

    Una rama es una línea de trabajo independiente. La rama principal se llama main y debería contener siempre la versión "buena". Cuando quieres probar algo, creas una rama, trabajas allí y, cuando está listo, la fusionas con main.

    Ejemplo práctico: añadir una sección de postres

    # Ver ramas (la del asterisco es en la que estás)
$ git branch
* main
# Crear una rama nueva y cambiarte a ella
$ git switch -c postres
Switched to a new branch 'postres'
$ echo "Flan: huevos, leche, azúcar" > flan.txt
$ git add flan.txt
$ git commit -m "Añade receta de flan"
[postres 1a2b3c4] Añade receta de flan
# Volver a main: ¡flan.txt desaparece de la carpeta! (sigue a salvo en su rama)
$ git switch main
Switched to branch 'main'
$ ls
README.md  tortilla.txt

    Cuando la rama está lista, la fusionamos con main. Siempre te colocas primero en la rama que va a recibir los cambios:

    $ git switch main
$ git merge postres
Updating 9c03f11..1a2b3c4
Fast-forward
 flan.txt | 1 +
# Ya no necesitamos la rama: la borramos
$ git branch -d postres
Deleted branch postres (was 1a2b3c4).
    ¿Fast-forward?Si main no ha cambiado desde que creaste la rama, Git simplemente "adelanta" el puntero de main. Si los dos han avanzado, Git crea un commit de fusión (merge commit) que une ambas historias.
    💡 switch o checkoutEn tutoriales antiguos verás git checkout rama y git checkout -b rama. Hacen lo mismo que git switch rama y git switch -c rama; switch es la forma moderna y más clara.

    En equipo, lo normal no es fusionar en tu ordenador, sino desde la web, después de que alguien revise los cambios:

    GitHub

    Se fusiona mediante un pull request (PR). Lo verás en el módulo 9.

    GitLab

    Se fusiona mediante un merge request (MR): es exactamente lo mismo con otro nombre. Lo verás en el módulo 9.

    Conflictos: cuando dos cambios chocan 💥

    Si en dos ramas se modifica la misma línea del mismo archivo, Git no sabe con cuál quedarse y te pregunta. Eso es un conflicto. No es un error: es Git pidiéndote que decidas.

    $ git merge picante
Auto-merging tortilla.txt
CONFLICT (content): Merge conflict in tortilla.txt
Automatic merge failed; fix conflicts and then commit the result.

    Al abrir el archivo verás unas marcas:

    <<<<<<< HEAD
Tortilla: huevos, patatas, cebolla, aceite, sal
=======
Tortilla: huevos, patatas, guindilla, aceite, sal
>>>>>>> picante
    1. Entre <<<<<<< HEAD y ======= está tu versión (la rama en la que estás). Entre ======= y >>>>>>>, la de la otra rama.
    2. Edita el archivo y déjalo como quieras que quede, borrando las tres líneas de marcas. Por ejemplo: Tortilla: huevos, patatas, cebolla, guindilla, aceite, sal
    3. Marca el conflicto como resuelto y termina la fusión:
    $ git add tortilla.txt
$ git commit -m "Fusiona rama picante"
# ¿Te has liado y quieres cancelar la fusión? (antes del commit)
$ git merge --abort
    💡 VS Code te ayudaAl abrir un archivo con conflicto, VS Code muestra botones: Accept Current Change, Accept Incoming Change, Accept Both Changes. Muy cómodo.

    Si el conflicto aparece en la web al intentar fusionar:

    GitHub

    El PR muestra "This branch has conflicts that must be resolved". Los conflictos sencillos se arreglan con el botón Resolve conflicts, que abre un editor en la web.

    GitLab

    El MR muestra "Merge blocked: merge conflicts must be resolved". Pulsa Resolve conflicts y elige Use ours / Use theirs en cada bloque, o edítalo a mano (Edit inline).

    Quieres llevar los cambios de la rama diseño a main en tu ordenador. ¿Qué haces?

    Has editado el archivo en conflicto y quitado las marcas. ¿Qué falta?

              Módulo 8 · Práctica

              Subir tu proyecto a GitHub o GitLab

              Conectamos tu repositorio local con uno en la nube. Así tienes copia de seguridad y puedes compartirlo.

              Paso 1 · Crear el repositorio en la web

              GitHub
              1. Pulsa el botón + (arriba a la derecha) → New repository.
              2. Repository name: recetario.
              3. Visibilidad: Public (todo el mundo puede verlo) o Private (solo tú y quien invites).

              5. Pulsa Create repository. Copia la URL HTTPS:
                https://github.com/tu-usuario/recetario.git
              GitLab
              1. Pulsa el botón + (arriba a la izquierda) → New project/repository → Create blank project.
              2. Project name: recetario. En Project URL deja tu usuario.
              3. Visibility Level: Private o Public.
              4. Desmarca "Initialize repository with a README": en GitLab viene marcado por defecto y, si ya tienes el proyecto en local, provoca un conflicto inicial.
              5. Pulsa Create project. Copia la URL de Code → Clone with HTTPS:
                https://gitlab.com/tu-usuario/recetario.git

              Módulo 9

              Colaborar: pull/merge requests, issues y forks

              Así trabaja en equipo casi todo el mundo que usa GitHub o GitLab.

              Issues: la lista de tareas del proyecto

              Un issue es una ficha para reportar un error, proponer una idea o apuntar una tarea. Tiene título, descripción, comentarios, etiquetas y una persona asignada. Cada issue tiene un número, por ejemplo #12.

              GitHub

              Pestaña Issues → New issue. Etiquetas en Labels (bug, enhancement…), persona en Assignees. Tablero tipo kanban: Projects.

              GitLab

              Menú Plan → Issues → New issue. Etiquetas en Labels, persona en Assignee. Tablero tipo kanban: Plan → Issue boards.

              💡 Truco (funciona en las dos)Si en un commit o en la descripción del PR/MR escribes Closes #12, al fusionarse en main el issue 12 se cierra automáticamente.

              Proponer cambios: pull request o merge request

              GitHub · Pull request (PR)

              Se numeran con #, igual que los issues: #15.

              GitLab · Merge request (MR)

              Se numeran con ! para distinguirlos de los issues: !15.

              Ambos significan lo mismo: "he hecho estos cambios en mi rama, ¿los revisas y los fusionamos en main?". Permiten que otra persona comente línea a línea antes de aceptar.

              El flujo completo

              1. Actualiza main y crea una rama para tu tarea.
              2. Trabaja y haz commits en esa rama.
              3. Sube la rama al remoto.
              4. Abre el PR/MR en la web.
              5. Revisión: los compañeros comentan; tú corriges con más commits en la misma rama (el PR/MR se actualiza solo).
              6. Merge: los cambios entran en main.
              7. Limpieza: actualizas tu main local y borras la rama.

              Pasos 1 a 3, en la terminal (igual en las dos):

              $ git switch main
$ git pull
$ git switch -c receta-paella
$ echo "Paella: arroz, azafrán, judía verde, pollo, conejo" > paella.txt
$ git add paella.txt
$ git commit -m "Añade receta de paella (closes #12)"
$ git push -u origin receta-paella

              Pasos 4 a 6, en la web:

              GitHub
              remote: Create a pull request for 'receta-paella' on GitHub by visiting:
remote:   https://github.com/tu-usuario/recetario/pull/new/receta-paella
              1. Abre ese enlace, o pulsa el aviso amarillo Compare & pull request de la página del repositorio.
              2. Comprueba base: main ← compare: receta-paella, escribe título y descripción → Create pull request.
              3. Revisores: pestaña Files changed → comentar líneas → Review changes → Approve.
              4. Merge pull request → Confirm merge, y después Delete branch.
              GitLab
              remote: To create a merge request for receta-paella, visit:
remote:   https://gitlab.com/tu-usuario/recetario/-/merge_requests/new?merge_request%5Bsource_branch%5D=receta-paella
              1. Abre ese enlace, o pulsa Create merge request en el aviso de la página del proyecto.
              2. Comprueba source: receta-paella → target: main, escribe título y descripción → Create merge request.
              3. Revisores: pestaña Changes → comentar líneas → botón Approve.
              4. Botón Merge. Deja marcada Delete source branch para que borre la rama remota sola.

              💡 Si escribes Draft: al inicio del título, el MR queda como borrador y no se puede fusionar hasta que lo marques como listo.

              Paso 7, de vuelta en la terminal (igual en las dos):

              $ git switch main
$ git pull
$ git branch -d receta-paella

              Fork: contribuir a proyectos de otras personas

              En repositorios ajenos no tienes permiso para crear ramas. La solución es un fork: una copia del repositorio en tu cuenta.

              GitHub
              1. En el repositorio original, botón Fork (arriba a la derecha) → Create fork. Se crea github.com/tu-usuario/proyecto.
              2. Clona tu fork, crea una rama, haz commits y push.
              3. En tu fork aparecerá Contribute → Open pull request: el PR va de tu fork al repositorio original.
              GitLab
              1. En el proyecto original, botón Fork (arriba a la derecha) → elige tu usuario como namespace → Fork project.
              2. Clona tu fork, crea una rama, haz commits y push.
              3. Create merge request, con target project = el proyecto original.

              Clone

              Copia un repositorio a tu ordenador.

              Fork

              Copia un repositorio a tu cuenta de GitHub o GitLab.

              Proyecto final: publica tu propia web gratis

              Juntamos todo lo aprendido (repositorio, commits, ramas, push y PR/MR) y el resultado es una página web real en internet con GitHub Pages o GitLab Pages.

              Lo que vas a construir

              GitHub Pages

              Tu web en https://tu-usuario.github.io/mi-web/. Se activa con dos clics en la configuración.

              GitLab Pages

              Tu web en https://tu-usuario.gitlab.io/mi-web/ (o una dirección única que GitLab te asigna). Se activa con un pequeño archivo de configuración: .gitlab-ci.yml.

              Paso 1 · Crear el proyecto local (igual en las dos)

              $ cd ~/Documents

$ cd mi-web

<body>
  <h1>¡Hola! Soy Tu Nombre 👋</h1>

              Paso 2 · Primer commit y subida

              GitHub

              Crea en la web un repositorio público vacío llamado mi-web (en el plan gratuito, Pages exige que sea público).

              $ git add index.html

$ git remote add origin https://github.com/tu-usuario/mi-web.git
$ git push -u origin main
              GitLab

              Crea en la web un proyecto vacío llamado mi-web (sin README). Puede ser público o privado: Pages funciona en los dos casos.

              $ git add index.html
$ git commit -m "Crea la página principal"
$ git remote add origin https://gitlab.com/tu-usuario/mi-web.git
$ git push -u origin main

              Paso 3 · Activar Pages

              GitHub Pages
              1. En el repositorio: Settings → Pages.
              2. En Build and deployment, Source: Deploy from a branch.
              3. Branch: main, carpeta / (root) → Save.
              4. Espera uno o dos minutos y recarga: aparecerá el enlace https://tu-usuario.github.io/mi-web/. ¡Tu web está en internet! 🌍
              GitLab Pages
              1. Crea en la carpeta del proyecto un archivo llamado exactamente .gitlab-ci.yml (con el punto delante) con este contenido:
              pages:
  image: alpine:latest
  script:
    - mkdir -p public
    - cp index.html public/
  artifacts:
    paths:
      - public
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH

              Le dice a GitLab: "cada vez que se actualice main, copia la web a la carpeta public y publícala".

              $ git add .gitlab-ci.yml
$ git commit -m "Configura GitLab Pages"
$ git push
              1. En la web: Build → Pipelines. Verás el proceso en marcha; espera a que se ponga en verde (passed).
              2. Deploy → Pages: ahí aparece la dirección de tu web. ¡Ya está en internet! 🌍

              Si el pipeline no arranca y pide verificar la cuenta, es la verificación de identidad que comentamos en el módulo 2.

              Paso 4 · Mejora con una rama y un PR/MR

$ git diff

$ git push -u origin aficiones
              GitHub
              1. Pulsa Compare & pull request, escribe una descripción y Create pull request.
              2. Revisa la pestaña Files changed: verás tus cambios en verde.
              3. Merge pull request → Confirm merge. En un minuto tu web se actualiza sola.
              GitLab
              1. Pulsa Create merge request, escribe una descripción y créalo.
              2. Revisa la pestaña Changes: verás tus cambios en verde.
              3. Pulsa Merge. Se lanzará un pipeline nuevo y, al terminar, tu web estará actualizada.

$ git branch -d aficiones

              Glosario

              TérminoDefinición
              Branch (rama)Línea de desarrollo independiente. La principal es main (en proyectos antiguos, master).

              CloneCopia local completa de un repositorio remoto.
              CommitInstantánea guardada del proyecto con mensaje, autor y fecha.
              Conflict (conflicto)Cuando Git no puede fusionar automáticamente porque dos cambios afectan a las mismas líneas.
              Detached HEADEstar situado en un commit concreto en vez de en una rama.
              FetchDescargar cambios del remoto sin fusionarlos (pull = fetch + merge).
              ForkCopia de un repositorio ajeno en tu cuenta de GitHub o GitLab.

              HashIdentificador único de un commit (ej. a3f9c21).
              HEADPuntero a "donde estás ahora": normalmente, el último commit de la rama actual.
              IssueFicha para reportar errores, ideas o tareas.
              MergeUnir los cambios de una rama en otra.

              NamespaceEn GitLab, el usuario o grupo al que pertenece un proyecto (la parte tu-usuario de la URL).
